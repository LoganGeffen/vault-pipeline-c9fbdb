The Vault module pipeline

A member chooses a module and submits one value or file. Supabase admits the job, GitHub Actions runs the selected Python or Docker package, and the callback stores its result privately. The browser follows job progress and requests an authorized download. Modules share the registry, runner and job contract.

The September 29 walkthrough follows two successful live jobs through Python and Docker. The live Vault uses a Skill Catalog and result visualizations that differ from the older frontend source pinned below; deployed frontend/backend parity is not implied by those source links.

Two authentication boundaries. Member requests use the user session and organization membership. Runner callbacks authenticate separately and validate state transitions. The module does not write directly to Supabase. Cleanup and failure reporting are attempted; neither is guaranteed merely because the workflow schedules them.

3Data modelentity–relationship

Quota comes from counting jobs in the billing period, not from a counter table. The admission RPC locks and revalidates subscription state before inserting the queued job. There is no jobs-to-subscription foreign key. Sources: identity and organizations, registry, quota and admission.

Where billing state and registry entries come from

Verified Stripe webhooks update stored subscription state; run admission reads that state rather than calling Stripe per job. Module release projects manifests through sync_modules into the registry. It does not deploy frontend code, SQL or edge functions. Billing contract · Release runs · Release source.
