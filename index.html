1Overview C4 · context and containers

The system in its surroundings

The boundary here is the member-facing Vault application and its backend. GitHub Actions supplies execution; Stripe supplies billing events. External scientific services are used only by particular modules.

Inside the Vault application

The web UI calls managed authentication, database and backend APIs. Backend functions admit jobs and authorize results. Private Storage holds file inputs and outputs. The execution service calls back with status and the result.

Supporting flows: billing, module release and publication

Billing. Hosted Checkout and verified Stripe webhooks update organization subscription state. Admission reads that stored state and applies git-owned entitlement/quota policy; it does not call Stripe for every run. Billing contract · Webhook · Open membership.

Registry release. Protected-main module changes trigger release-modules.yml, which sends validated contracts through the callback’s sync_modules action into compute_modules. Open release runs · Release source.

Publication. Git source, Supabase deployment/data, and Lovable editor/publication are separate surfaces. Registry release does not deploy SQL, edge functions or frontend code. System boundaries.

3Request sequence UML · sequence

Accepted dispatch returns before execution finishes. The job-board polling loop overlaps the runner’s work. The drawing expands a representative file run; a value run skips private input staging and retrieval.

Read the sequence as text
  1. Load the registry contract; submit one value or file.
  2. Authenticate, validate input and organization, then check stored entitlement and atomically reserve quota with a queued job.
  3. Stage an optional private input and dispatch GitHub Actions. A 4xx rejection fails the job and returns 502; transport/5xx uncertainty leaves it queued and returns 202 with a warning. Accepted dispatch returns 202 with the job ID.
  4. The browser refreshes its organization-scoped job board and polls every five seconds while active jobs exist.
  5. In parallel, the runner resolves the package, reports running, prepares Python or Docker, retrieves any file input and executes under the declared timeout.
  6. Validate the declared output. The callback stores a unique private object, conditionally records succeeded and attempts input cleanup. Failure callbacks attempt to mark failed.
  7. When the member downloads, get-result checks job membership and succeeded state, then returns a 60-second URL for the exact object.

Cleanup and failure callbacks are attempts, not guarantees. An uncertain dispatch may remain queued until execution or another recovery mechanism resolves it; a live recovery scheduler was not verified for this review.

4Runtime data entity–relationship

The registry is a projection of module contracts. Jobs hold organization scope and lifecycle; the exact result object lives in private Storage. Billing-period usage is derived from job history.

Read the data relationships as text
  • Profiles reference auth users and a preferred organization. Membership comes from organization_members.
  • Organizations own jobs and subscription records. Subscription state supplies admission policy and the current counting period.
  • Admission logic locks and revalidates the subscription, counts period usage from jobs, and inserts the queued job atomically. No separate quota-counter table or jobs-to-subscription foreign key exists.
  • jobs.module is a validated logical compute_modules slug, not a foreign key.
  • File input is transient at job-inputs/<job_id>/<input_name>. jobs.result_ref names the exact private job-results/<job_id>/<attempt>/<basename> object.
