    The release map

    Read from top to bottom. The numbered key explains what to do and where to check it. The dashed step is the initial backend setup; ordinary manifest maintenance skips it.

    After setup: edit the manifest → review and merge → wait for registry release → check the Vault. Repeat steps 1–4 and 6 for name, description, visibility and enabled status.

    Key to the release map

    1. Prepare the module and its starting state

      Add the implementation, dependencies, manifest, validation fixture and output assertion. Start a new module disabled and hidden. For the recorded example, include the initial Silver entry in MODULE_ACCESS.

      See this step

      Authoring guide · Prepared Training Echo files · Initial Silver policy patch. Training Echo accepts text and returns its character count in a CSV; it is a pipeline example, not a scientific model.

    2. Validate the exact change being reviewed

      Run the fixture and check the actual output contents. Review the PR diff and require passing checks on its latest commit before merging.

      See this step

      Local acceptance script · Example validation result · Recorded initial PR #54.

    3. Merge through the reviewed PR

      Merge into main. Changes under the module and release paths trigger release-modules. A merged PR alone does not establish that the release succeeded.

      See this step

      Open pull requests · Release workflow and trigger paths.

    4. Verify the automatic registry release

      Wait for a successful release-modules run, check its actual checkout commit, and verify the intended compute_modules row. This releases manifest settings into Supabase.

      Name and description update catalog text. Visible controls discovery and the generic launcher. Enabled controls new submissions. Keep both enabled and visible to see renamed catalog text; hiding alone does not block an authorized direct submission.

      See this step

      Open registry release runs · Open database · Manifest projection source. Disabling a module preserves its job history and results.

    5. Complete the initial backend setup

      The recording sets Silver once by manually deploying submit-job after the initial merge and deployment checks. This deploys the whole function. Subsequent manifest-only edits skip this step; a later tier-policy change would need a separate backend deployment.

      See this step

      Deployment prerequisites · Tracked tier policy · Open Edge Functions. Silver is the historical walkthrough setting, not a claim about the current live tier.

    6. Verify the result in the live Vault

      For launch, enable and reveal the module through the same manifest PR and release flow. Refresh the catalog, run a known input with an entitled account, and inspect the successful job and downloaded output. For maintenance, verify the specific setting you changed.

      Publish frontend code only if the live UI needs a code change. The recorded manifest updates needed no separate frontend publication.

      See this step

      Open Skill Catalog · Open Runs · Recorded enablement PR #56. PR #57 also hid the module, so its footage demonstrates hiding rather than the renamed card. PR #59 disabled and hid Training Echo after the demonstration.
